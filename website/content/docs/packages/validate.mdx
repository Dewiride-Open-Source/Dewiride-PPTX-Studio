## What it is

PowerPoint repairs or refuses a file silently, and names no part and no line when it does. `@pptx-studio/validate` runs 29 rules over a package - half derived from the schema, half from decks PowerPoint declined one change at a time - and reports findings with a part, an XPath and whether the problem was introduced by this session or inherited from the file.

`assertValid` throws rather than returning a boolean, so a writer cannot hand over bytes it just broke.

## Key concepts

### Findings are not errors

`validatePackage` never throws for a finding; it returns them. A rule that could not run is listed under `skipped` with the reason - reported nothing and found nothing are opposite meanings.

### Two halves: derivable and measured

Each rule carries its `evidence`: `schema` for a rule ECMA-376 states, `measured` for one found by making PowerPoint refuse a file, `both` when both hold.

### "Did we break it", not "is it valid"

With a baseline, each finding says whether it was `introduced` or `inherited`. A deck that was already broken can still be exported without making it worse.

### What passing does not mean

The rules are the ways PowerPoint is known to refuse a file, not every way it could. No hosted runner has Office, so "opens in PowerPoint" is measured by hand.
